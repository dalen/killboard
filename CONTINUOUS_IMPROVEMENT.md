## API-blocked backlog

These are feature-specific blockers, not project blockers:

1. Ordered, batched, bounded Recent Teammate History with deterministic newest-first order and per-character coverage metadata. Existing scenario connection lacks an order argument; alias probing duplicated rosters and was too costly. Exact resolver contract and evidence are preserved in the comparative ledger.
2. Item live-state and race-aware eligibility filters; global acquisition-source filters applied before pagination/counts.
3. Creature loot groups with readable conditions, eligibility and possible-versus-guaranteed semantics.
4. Efficient grouped scenario map/tier/queue/career/role/guild aggregates with exact denominators and sample counts. Basic date-bounded totals, winner shares and API-provided means are implemented; do not use browser-side first-N data to claim exhaustive group rankings.
5. Histogram/percentile instance distributions and authoritative feed freshness/ingestion metadata; current median/average values do not supply those facts.
6. Efficient open-world-only kill filtering: the bounded `instanceId eq null` query timed out. Do not use this filter in product code; investigate after API change or a server-approved bounded test.
7. Canonical pairing-wide comparisons and authoritative campaign outcomes: public API lacks a canonical zone-to-pairing membership and campaign result contract. Selected-zone activity comparisons are available locally; pairing comparisons must wait for explicit membership data and must never infer outcomes from kills.

## Infrastructure-dependent backlog

1. Authoritative Campaign Chronicle: needs server events for zone locks, keep/fortress transitions, city results, campaign/pairing IDs, UTC timestamps, corrections and retained coverage. Kill totals remain activity evidence only and must never establish a winner.
2. Live population, online-time and retention/cohort views: require a trustworthy live roster or historical presence/login collection and explicit coverage/retention semantics.
3. Broad activity time series and historical comparisons beyond currently bounded public aggregates: require efficient collection/aggregation and freshness metadata, not browser scans.
4. Any new long-retention or cross-period dataset must define provenance, missing-data behavior, refresh cadence and player-facing coverage before implementation.

## Rejected design decisions

- No inferred campaign/zone-lock/fort/city winner from kill totals or feed paths.
- No “premade” claim from repeated teammate or same-guild co-appearance; use neutral participation language.
- No population census claims from characters observed in recorded kills.
- No unbounded scenario or kill scans in the browser, and no rankings presented as exhaustive when based on a page/sample.
- No copy-link, copy-summary or CSV controls unless a concrete user need is established; existing filters are URL-backed.
- No private Emissary endpoints, D1, Workers, credentials, dashboards or staff data in the official `dalen/killboard` patch.
- Do not restore a separate Kills leader card or label the scoreboard's Kill Damage leader simply “Damage.”
- Do not add an “Equipped set progress” summary to character Armory. The user rejected it as unnecessary and too tall, pushing equipped Armor/Weapons/Jewellery/Event Item lower on the page. Keep the existing gear slot displays and existing item-level set details.

### Recent Teammate History feasibility conclusion (2026-11-26)

Do not implement client-side from the current schema. `ScenarioRecordFilterInput` can express `startTime.lt` and `scoreboardEntries.some.characterId.eq`, but generated `QueryScenariosArgs` has no ordering input. A live `scenarios(first:50)` request returned scenario start times in nonchronological order. Therefore `first:N` per character cannot be relied on to select the latest N appearances, and retrieving every earlier scenario to sort client-side would be unbounded. `Character` exposes no scenario history connection.

A live bounded-alias probe for the populated 10-player Garden of Morr match returned 30 rows per each of ten participants in one GraphQL HTTP request in 1,191ms with a 313,520-byte response. It duplicated scenario roster data for every alias, while current matches can reach at least 36 players (observed in the live API's latest 50 scenario records). This is evidence the alias approach is possible but not an efficient, ordered data contract for the feature.

Exact Dalen API addition requested: a batched resolver such as `scenarioTeammateHistory(characterIds: [ID!]!, before: DateTime!, limit: Int!): ScenarioTeammateHistory!`, capped at 30 and strictly excluding scenarios whose `startTime >= before`. Return a de-duplicated set of scenario appearances ordered newest-first, with scenario ID/name/start time and only the requested current-match participant IDs plus their team/realm; also return per-participant coverage metadata (`hasMore` or an explicit complete-through/retention indicator). The resolver must define deterministic descending time order, apply the bound and per-character latest-N selection server-side, and avoid scanning or returning all earlier history. One request should supply all current match participants; no per-combination resolver calls. This supports honest last-10/20/30-window counts/streaks, teammate profile links, and responsive client rendering. Consecutive-streak definition still needs to be displayed in-product: count successive scenario appearances involving any group member where all group members participated together on the same realm; scenarios involving none of that group do not break the streak. Do not call groups premades.
